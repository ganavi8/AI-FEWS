## Product outcomes

1. **Shared web application and location workflow.** React + TypeScript responsive SPA; preserve the dark compact sidebar, cyan operational highlights, accessible controls, and concise Location workspace. `/location` remains available; navigation becomes functional for Dashboard, Location, Environment, Risk, Alerts, Map, Community Reports, Trends, Data Quality, Sources, Preparedness, Emergency, Simulator, Saved Locations, Notifications, Settings, Privacy, and About. `/` opens Dashboard. No default city or invented observations. Browser geolocation is requested only after an explicit user action, once; Android location uses the same consent-first flow. Manual latitude/longitude validation enforces `-90..90` and `-180..180` in client and server. A place-name lookup is an explicit action, not an automatic side effect of location selection.

2. **Real provider-backed environmental data.** The Node/TypeScript API calls Open-Meteo forecast and air-quality services using server-side adapters and bounded timeouts; normalized records carry provider/source, the provider observation time where available, `fetchedAt`, freshness/status, coverage and limitations. Current/forecast conditions include temperature, precipitation/rainfall, precipitation probability, wind, humidity, pressure, condition and forecast where the provider supplies them. Nominatim reverse geocoding is proxied only on explicit request, cached, globally throttled to no more than one request per second and sent with an application-identifying User-Agent. Runtime provider/base-URL configuration stays switchable without a frontend release. Leaflet requests only visible OSM tiles and includes visible OSM attribution and a compliant referrer; OSM tiles are **not** prefetched or cached for offline use. Satellite, terrain, hydrology and historical-flood endpoints return `CONFIGURATION REQUIRED` until a real provider is configured; no simulated data is returned as real data.

3. **Single authoritative risk and transparent data quality.** One backend `RuleBasedHeuristic-v1.0` calculation feeds web and Capacitor views through `/api/risk` and `/api/risk/explain`; there is no second client-side algorithm. The canonical levels are `LOW`, `MODERATE`, `HIGH`, `VERY_HIGH`, `UNKNOWN`; insufficient real observations produce `UNKNOWN` and `Insufficient environmental data`. Only genuinely calculated score/factors are returned. `probability`, `confidence`, and `uncertainty` remain `null` unless a validated model actually supports them. A source/freshness/data-quality explanation and decision-support/official-emergency disclaimer accompany the result. UI references to `CRITICAL` in older material do not override the explicit backend `VERY_HIGH` contract.

4. **Persistent alerts and notifications.** The server derives alerts from real environmental/risk observations and threshold transitions, with unique ID/fingerprint, location, severity, reason, source, created/expiry timestamps, data quality, recommended action and database deduplication. Client screens only display stored server alerts; clients do not create them. All server-side notification categories default off until an installation explicitly saves preferences; device permission and local display opt-in are separate choices, and permission is requested only at an enabling action. Alert evaluation is tied to an explicit refresh or live assessment; the attachments define no recurring cadence and prohibit unjustified polling, so no off-session scheduler or guaranteed push-delivery claim is made. Notifications are not claimed as verified until device delivery can be tested.

5. **Community reporting and moderation.** Reports require `clientId`, category, description (maximum 500 characters), latitude, longitude, `createdAt`, and status; invalid coordinates/content are rejected. `clientId` is stable and protected by a MySQL uniqueness constraint. `COMMUNITY GENERATED` is provenance, sync lifecycle is separately represented as `PENDING SYNC`, `SYNCING`, `SYNCED`, `FAILED`, and moderation is separately `SUBMITTED`, `PENDING_REVIEW`, `VERIFIED`, `REJECTED`, or `EXPIRED`. Reconcile the sample SQL's nullable coordinates in favor of the explicit required-input contract: API and database require coordinates. Public map queries expose only verified reports and always distinguish community observations from official/provider data. Moderation is server-authoritative, requires server-only `MODERATION_TOKEN`, and safely reports `MODERATION_NOT_CONFIGURED`/503 while that secret is absent; no token is put in client code.

6. **Durable MySQL, saved locations and genuine history.** Enable managed server + MySQL only after telling the owner this capability is one-way and that Webdev development and publication share the same database. `DATABASE_URL` is server-only. Commit deterministic, additive, version-tracked migrations for `community_reports`, `alerts`, `saved_locations`, time-series snapshots, idempotency/rate-limit coordination, and Nominatim throttling/cache where needed. Do not seed fictitious domain observations. Reports/alerts/saved places persist and can be queried after restart. Since user login is optional and absent, opt-in saved places are bound to an unguessable, browser/app-local anonymous owner key; the server stores only a keyed hash, not raw keys or request coordinates in logs. The UI explains that this is per-browser/app installation, not an account or cross-device sync. History is stored only after a place is explicitly saved; unsaved location lookups are not durably logged. An actual provider result temporarily served from the server cache may be attached to a location only after the user explicitly loads that saved place, using the original source timestamp and duplicate-safe location/time keys; the age shown is recomputed from the provider's observation time.

7. **Offline-first PWA and local privacy controls.** Installable application-owned web manifest, icons, theme colors, HTTPS production, service-worker app shell and responsive offline experience. Use IndexedDB database `aifews-offline`, stores `snapshots`, `reports`, `preparedness`. Cache the app shell, local preparedness and timestamped client-side environmental snapshots; never blindly cache API responses or OSM tiles as current/offline truth. Offline reports persist locally with stable IDs, show `PENDING SYNC`, recover after reload/restart, retry with exponential backoff on reconnection, and become `SYNCED` only after server confirmation; duplicate prevention is enforced in MySQL. Offline status distinguishes `LIVE`, `CACHED`, `STALE`, and `UNAVAILABLE`, and shows original source time. Privacy Center can clear local snapshots, queued reports, cached preparedness and local preferences; it explains that local clearing is not server deletion. Saved-place server deletion remains explicit.

8. **Preparedness, simulation, trends and policy pages.** Preparedness covers before/during/after heavy rain/flooding, road and electrical safety, evacuation preparation, emergency kit, communications and rural/farm safety; it is available offline and says to follow official emergency instructions. Trends show actual persisted observations only; no fake historical flood values. The scenario simulator is server-authoritative, visibly `SIMULATION`, offers `NORMAL`, `HEAVY RAIN`, `EXTREME RAIN`, `DRAINAGE FAILURE`, `HIGH FLOOD RISK`, is never mixed with live observations, and stores no simulation as real history. Data Quality exposes provider/source/latest update/freshness/status/coverage/limitations. The app has a Privacy Center and a directly addressable `/privacy-policy` public page covering location, provider requests, saved locations, reports, notifications, backend processing, retention/deletion, third parties and contact. Absent contact details are marked `NOT CONFIGURED`, not invented; final operator review is still required.

No backend secret, database DSN or signing key enters bundled web assets or APK. The Sandbox has Node/npm/pnpm and only a JRE; it has no `javac`, Gradle, Android SDK tools or emulator, and no signing credential is configured. Generate/sync the Android project where tooling permits; a release AAB/APK build and device permissions/notification tests are hard blockers until a JDK/Android SDK/device and valid owner-controlled signing key are available. Do not report an Android build that has not run.

10. **Security, errors, APIs and validation.** REST endpoints use shared TypeScript request/response contracts, server/client and server-side validation, parameterized SQL, same-origin CORS, rate limits, request-size limits, structured errors/HTTP status, provider timeouts/failure handling, safe request logging without raw coordinates/secrets, safe moderation authorization, and production headers compatible with Webdev Preview. Configure health/readiness and accurate database/provider states. Automated tests cover the specified backend, client routes/modules and offline transitions; typecheck/build and actual provider/API parsing are verified. MySQL INSERT/SELECT/deduplication/restart persistence and privileged moderation are only marked PASS if real environment evidence exists. Android launch/device acceptance remains NOT VERIFIED when no SDK/device is available.

## Serving, build and caches

Use a mixed static-frontend/API-container deployment, not an empty-shell SSR server: Vite emits `dist/client`; the Node container runs Express on the hosting-provided `PORT` and can serve a bundled fallback for direct app startup. Static `build.command` is self-contained: enable/pin pnpm `11.25.0`, frozen-lockfile install, then client build; `build.outputDirectory` is `dist/client`. Dockerfile independently installs via the committed policy, builds the required app/server assets, starts the production Node listener and runs versioned idempotent migrations/readiness. Declare `features.server: true` and `features.database: true`, then `deploy.dockerfilePath: Dockerfile`, `deploy.healthPath: /api/health` once the listener is ready.

Ordered published paths: `/api/*` → `server`, `cache: no-cache`; `/sw.js` → `static`, `cache: no-cache`; `/assets/*` → `static`, `cache: immutable`; `/*` → `static`, `spaFallback: true`. This ensures missing APIs/assets are not disguised as HTML while real React page routes work on refresh. Keep mutable HTML re-fetchable, fingerprinted Vite assets immutable, service worker immediately updateable, and API/personal data out of shared caches. Select `pwa.manifestMode: application_owned`; route rules apply on published deploy, not Preview. Static and container builds both use the same checked-in pinned package manager/lifecycle policy. Do not add `X-Frame-Options: SAMEORIGIN/DENY` or a restrictive CSP `frame-ancestors`; Preview is a cross-site iframe.
